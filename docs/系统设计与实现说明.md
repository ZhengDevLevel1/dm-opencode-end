## 1. 整体设计描述

### 1.1 系统目标

本系统是一个面向花店的 B/S 架构电商管理与推荐平台，围绕"花礼销售"场景，提供从商品浏览、个性化推荐、购物车、下单支付、履约配送到评价售后的全链路能力，并兼顾门店店员与系统管理员的管理诉求。

系统核心研究点：**基于内容与行为融合的鲜花推荐算法**，通过 TF-IDF 文本特征、用户行为画像、品类分布、节日季节上下文、热度与评分等信号的综合加权，为每位顾客生成个性化推荐列表，并支持离线五类人设评估。

系统使用角色：

| 角色 | 主要能力 |
| --- | --- |
| 顾客 CUSTOMER | 浏览/搜索商品、获取智能推荐、购物车/收藏、下单/模拟支付、评价、申请售后 |
| 店员 STAFF | 库存管理（调整与流水）、订单接单与履约节点推进、售后审批 |
| 管理员 ADMIN | 用户/商品管理、推荐权重与日志、评价审核回复、操作日志、经营统计 |

### 1.2 总体架构

系统采用**前后端分离**架构：

- 后端：模块化单体的 Spring Boot 应用，对外提供 RESTful JSON 接口，统一前缀 `/api`，JWT Bearer 认证，统一 `ApiResponse` / `PageResult` 响应封装与全局异常处理。
- 前端：React 单页应用，通过 TanStack Query 管理服务端状态、Zustand 管理客户端主题状态，路由级角色守卫控制页面访问。
- 基础设施：MySQL 8 主数据库，Redis 用于 Token 会话与可选的缓存加速（可降级为内存实现），MinIO 对象存储承载图片上传，H2 用于后端自动化测试。

```text
浏览器 (React SPA)
   │  HTTPS/JSON + JWT Bearer
   ▼
Spring Boot 后端（Controller → Service → Mapper）
   ├── MySQL 8（业务数据）
   ├── Redis（会话/缓存，可禁用降级）
   └── MinIO（图片对象存储）
```

### 1.4 后端分层与模块划分

后端按“**模块化单体**”组织，控制器调用服务层，服务层基于 MyBatis-Plus 映射器，每个业务模块自持实体与 DTO：

| 模块 | 职责 |
| --- | --- |
| `auth` | 注册/登录/登出、JWT 签发、当前用户 |
| `user` | 个人资料、改密、管理员用户管理 |
| `product` | 商品目录/搜索/筛选/详情、管理员 CRUD 与上下架 |
| `inventory` | 人工库存调整与库存变动流水 |
| `cart` / `favorite` | 购物车数量校验（上限 99、不超库存）、收藏 |
| `order` / `payment` | 下单原子扣库存、取消、售后；模拟支付与幂等回调 |
| `fulfillment` | 接单与履约节点推进 |
| `review` | 商品评价、防重复评价、管理员回复与审核 |
| `recommendation` | 核心推荐引擎、行为画像、权重、日志、人设评估 |
| `stats` / `dict` | 经营统计图表、品类/状态等字典 |
| `log` | AOP 操作日志记录与查询 |
| `file` | MinIO 图片上传（头像/商品图/背景图） |

支撑层：`common`（统一响应/分页/枚举/异常）、`config`、`security`（JWT 过滤器/令牌存储）、`support`（缓存服务与键管理）。

### 1.5 核心业务流程

- **认证**：登录签发含 `userId/username/role/jti` 的 JWT；登出吊销服务端会话；Token 存储启用 Redis 时入 Redis，否则内存兜底。
- **购物与下单**：下单时以条件更新（`stock >= 数量`）原子扣减库存并写入库存流水；模拟支付回调将订单从 `PENDING_PAYMENT` 推进到 `PAID` 并累加销量，回调幂等。
- **履约**：店员接单后按 `ACCEPTED → PREPARING → DELIVERING → SIGNED` 顺序推进，非法跳转被拒绝，签收即完成。
- **售后/退款**：仅已完成订单可发起售后；审批通过则退款、回补库存、回退销量，拒绝则恢复 `COMPLETED`。
- **推荐**：综合 TF-IDF 余弦内容相似度、购买/收藏/评价行为、品类分布、收藏标签、节日季节上下文、热度与评分加权排序；冷启动用户回退节日季节 + 热度；管理员可调四项权重并运行五类人设 Top-10 离线评估。
- **一致性**：库存、销量变化后统一失效商品详情与热榜缓存，保证各端数据一致。
- **图片上传**：登录用户可上传 JPG/PNG/WEBP/GIF（≤5MB）至 MinIO，前端上传前支持拖拽平移 + 滚轮/滑块缩放裁剪（头像与商品图 1:1、背景图 16:9，GIF 动图自动跳过裁剪）。

### 1.6 接口与数据约定

- 全部业务接口前缀 `/api`，共 **70 个端点**（覆盖公开、登录、店员、管理员四类权限），与源码逐条核对一致，完整清单见 `docs/backend-api.md`。
- 统一响应 `ApiResponse{code,message,data,timestamp}`，分页统一 `PageResult{records,total,page,size,pages}`。
- 枚举一律大写字符串（如 `PENDING_PAYMENT`）；金额/评分使用 `BigDecimal`；时间无时区后缀的 `yyyy-MM-ddTHH:mm:ss`。
- 演示账号：`admin/admin123`、`staff/staff123`、`customer/customer123`、`alice/alice123`、`bob/customer123`。

## 4. 调试与测试结果描述

- 后端自动化测试基于 H2（MySQL 兼容模式），Redis 与 MinIO 关闭，验证纯业务逻辑与接口链路。

`mvn -B -ntp test` **32/32 全部通过**，覆盖推荐行为特性、五类人设评估指标、全季节（ALL）匹配、缓存失效、无效季节参数 400、购物车数量上限、权重舍入校验、文件上传入口与禁用兜底等关键路径。

### 4.3 前端静态校验

`npm run typecheck`、`npm run lint`、`npm run build` 均通过；`lint` 仅剩 5 个历史遗留的 react-refresh 提示性警告（0 错误），生产构建 3380+ 模块全部成功。

### 4.4 接口文档一致性核对

`docs/backend-api.md` 的端点表与源码逐条比对：**70 个源码端点与 70 个文档端点完全一致**，无遗漏、无多余。

### 4.5 图片上传链路冒烟验证

- `avatar / product / background` 三类图片上传均返回 200，MinIO 公共 URL 可直接访问（HTTP 200）。
- 头像设置与清空（`PUT /api/auth/me`）全链路验证通过，头像字段持久化到 `sys_user.avatar_url`。
- 裁剪组件验证：拖拽平移、滚轮/滑块缩放、按比例输出（头像 1:1、背景 16:9）、GIF 自动跳过裁剪。

### 4.6 典型问题调试记录

| # | 问题现象 | 原因与解决 |
| --- | --- | --- |
| 1 | 高并发下单可能超卖 | 普通查询后更新存在竞态；改为「条件更新」`stock >= quantity` 原子扣减并写流水，不满足即回滚 |
| 2 | 支付回调重复触发导致状态错乱 | 回调按支付单号幂等处理，已支付状态重复回调直接返回原记录 |
| 3 | 新用户推荐为空 | 增加冷启动通道：回退节日季节 + 热度信号，保证首次访问也有合理推荐 |
| 4 | 库存/销量变化后其他页面数据陈旧 | 订单、支付、取消、退款各路径统一失效商品详情与热榜缓存 |
| 5 | MinIO 未配置时上传报 500 不明确 | 增加 `FILE_UPLOAD_DISABLED`（503/8001）兜底并给出配置提示 |
| 6 | 推荐日志“重置后点击同一昵称不生效” | 关键词只存本地 state 未同步 URL，相同 URL 不触发 effect；改为 `setSearchParams` 同步 + 昵称链接 `onClick` 主动应用关键词 |
| 7 | 设置页滑动条（缩放/遮罩/模糊）拖拽一卡一卡 | 受控 input 每帧以旧值重渲染导致滑块回跳；改为非受控 + 值按帧合并上报，并将设置页改为细粒度订阅，拖拽时仅小范围重渲染 |
| 8 | 动画 GIF 裁剪后失帧 | canvas 无法保留 GIF 动画；裁剪流程对 GIF 自动跳过、直接上传原图 |

## 5. 项目总结

### 5.1 心得体会

- **前后端契约先行**：先沉淀统一响应、分页、枚举与错误码约定，再同步推进前后端，联调成本显著降低；70 个端点与文档零偏差印证了契约的价值。
- **一致性比功能更考验设计**：库存扣减、销量回退、缓存失效、幂等回调等细节决定了系统在真实场景下的可信度，"条件更新 + 流水留痕 + 缓存失效"三件套是本项目收获最大的实践。
- **推荐系统中冷启动与可解释性的重要性**：仅算法得分高不够，能说清"为什么推"（画像、标签、上下文的可视化日志与评估）与"冷用户推什么"（季节节日热度兜底）才是闭环。
- **工程化习惯**：自动化测试、类型检查、文档与代码互校，让每次重构和修复都有安全网，多次复杂改动得以快速收敛。

### 5.2 主要成果

1. 完成花店管理系统全链路（顾客/店员/管理员三角色，70 个接口）的设计、开发与自测，后端 35/35 测试通过，前端三项校验通过。
2. 实现以"内容相似度 + 行为画像 + 上下文"多路信号融合为核心的**可运营推荐系统**，支持权重在线调整、五类人设离线评估与逐条日志追踪。
3. 落地了完整的商品图片/头像/背景图上传与**前端裁剪**能力（拖拽、滚轮缩放、按场景定比例），并打通 MinIO 公共访问链路。
4. 完成强个性化的前端主题系统（配色/密度/圆角/背景）、库存卡片/流水双视图、管理端仪表盘与推荐运营页等 20+ 页面。
5. 沉淀了 6000+ 行的面向前端 API 文档与覆盖全部接口的说明文档，为后续维护与二开提供了完整参考。

### 5.3 存在不足及优化方向

**当前不足**

- 推荐未建模**地点/门店维度**：查询参数 `scene` 已预留但暂不影响结果，跨区域花材与运费差异未体现。
- Redis 仅用于会话与少量缓存，**真实环境下的 Redis 加速、限流、分布式场景未做端到端验证**；自动化测试在 H2 上完成。
- 前端暂无自动化测试套件，回归主要依赖类型检查与构建。
- 支付为模拟回调，未接入真实支付网关；无消息队列，库存/销量统计的最终一致性依赖同步路径。
- 图片裁剪对 GIF 动图自动跳过，不支持保留动画的裁剪。

**优化方向**

1. 推荐升级：引入向量检索/ES、协同过滤与深度排序模型（如双塔/DeepFM），加入地点与价格敏感度特征，并建立 A/B 实验评估线上收益。
2. 引入消息队列（如 RocketMQ）做订单事件驱动的库存、销量、日志异步解耦，配合幂等消费增强扩展性。
3. 补齐生产化能力：接入真实支付与短信通知、Redis 全面缓存与限流、监控告警（如 Actuator + Prometheus）。
4. 前端补建 Vitest + React Testing Library 测试体系，并为核心组件补视觉回归。
5. 裁剪支持动图逐帧处理或改用服务端裁剪，进一步降低大图上传带宽与存储成本。
