## 问题 1：介绍项目的整体功能、使用者、用了什么技术

**一句话答案：**
这是一个「花店电商 + 智能推荐」系统。消费者买花、店员履约、管理员运营，推荐算法是核心研究点。

### 1.1 三类使用者与功能

| 角色 | 能做什么 |

| 管理员 ADMIN | 用户管理（增改、改角色、禁用、重置密码）、商品管理（上下架、编辑、删除）、推荐运营（调权重、看日志、跑评估）、评价管理（回复/隐藏）、统计看板、操作日志、登录页外观设置 |

## 问题 2：难点一——推荐系统怎么做到"准"、能解释、可评估

**一句话答案：**
把推荐拆成四路信号（内容相似度、行为画像、节日季节、热度评分），用可配置权重融合；新用户走冷启动兜底；每次推荐都记录分数明细和理由，并用 5 个人设做 Top-10 离线评估。

### 2.1 难在哪

1. 新用户没有任何购买/收藏/评价，协同过滤直接失效。
2. 只按销量推荐，结果同质化，体现不出"个性化"。
3. 推荐结果如果是黑盒，答辩和运营都无法判断好坏。

### 2.2 怎么解决

**第一步：把商品变成向量（内容侧）**

- 用商品名称、品类、花语、场景标签、节日标签、季节构造文档；
- 花语做二元分词（bigram），中文无需引入分词框架；
- 计算 TF-IDF：`tf = 1 + log(count)`，`idf = log((N+1)/(df+1)) + 1`；
- 向量归一化后，用**余弦相似度**衡量"用户画像"和"商品"的接近程度。

**第二步：把用户行为变成画像（行为侧）**

| 行为 | 权重 |
| --- | --- |
| 购买 | `2.0 × min(数量, 5)` |
| 收藏 | `1.5` |
| 评价 | `1.2 × 评分 / 5` |
| 品类分布 | `4.0 × 该品类占比` |
| 偏好标签 | `1.5` |

行为向量与"当前节日/季节"的上下文向量按置信度融合：

```
confidence = clamp(0.55 + 0.20 × 购买频率 + 0.15 × 平均评分, 0.55, 0.90)
最终画像 = 行为画像 × confidence + 上下文画像 × (1 - confidence)
```

> 行为越多，越相信用户历史；行为少，就更依赖节日/季节。这是"冷启动"的平滑过渡，不是硬编码 if/else。

**第三步：四维加权排序**

```
finalScore = 0.4 × 内容相似度
           + 0.2 × 热度（log 归一化销量）
           + 0.25 × 节日季节契合度
           + 0.15 × 评分
```

- 权重存在 `recommendation_weight` 表，管理员可在线调整，DB 有 `CHECK` 约束保证和 ≈ 1；
- 先用相似度筛出候选池（默认 60 个，`candidate-limit`），再精算分数，避免每次全表打分。

**第四步：冷启动兜底**

用户无行为时，`coldStart = true`，直接用"节日/季节匹配 + 销量热度 + 评分"排序，保证新用户第一次打开也有合理结果。

**第五步：可解释 + 可评估**

- 每个商品返回 `contentScore / popularityScore / festivalScore / ratingScore / finalScore` 和一句理由，例如"与你近期偏好的「玫瑰」相符；热销商品，已售 128 件"；
- 每次请求写 `recommendation_log`：场景、节日、季节、是否冷启动、权重快照、商品 ID、分数明细；
- 后台"效果评估"构造 5 个人设，各取 Top-10，计算 **HitRate、Precision@10、单人覆盖率、整体覆盖率**。

### 2.3 追问速答

- **为什么不用协同过滤？** 单机数据量小、用户重叠稀疏，协同过滤效果不稳定；TF-IDF + 行为画像不依赖其他用户，冷启动更可控。
- **推荐结果会变吗？** 会。权重调整只影响后续请求，历史日志保留当时的权重快照，可复现。
- **怎么证明有效？** 用固定人设做离线评估，看 Precision@10 和覆盖率；同时日志能定位"为什么推这个"。

## 问题 3：难点二——下单怎么保证不超卖、状态不错乱

**一句话答案：**
不在 Java 里"先查再减"，而是把判断和扣减合并成一条带条件的原子 `UPDATE`；订单、支付、履约全部用"当前状态 = 期望旧状态"的条件更新，用影响行数判断成败，再配合事务回滚。

### 3.1 难在哪

1. 两个用户同时买最后 1 件，都查到"库存 1"，都下单 → 超卖。
2. 一次下单多件商品，第 3 件库存不足，前 2 件不能真的扣掉。
3. 支付回调可能重复到达，不能重复加销量。
4. 取消、售后退款要把库存补回去，且销量不能减成负数。

### 3.2 怎么解决

**① 防超卖：条件更新**

```sql
UPDATE product
SET stock = stock - #{quantity}, version = version + 1
WHERE id = #{productId}
  AND stock >= #{quantity}
  AND status = 'ON_SALE'
  AND deleted = 0;
```

- 判断和扣减在同一条 SQL 里，InnoDB 行锁保证原子性；
- 返回 0 行 → 说明库存不够或已下架 → 抛 `2003 库存不足`，带商品名；
- 不依赖 JVM 锁，单库部署天然安全。

**② 多商品：事务 + 排序**

- `create()` 标 `@Transactional`，任意一件扣减失败抛运行时异常，整个事务回滚；
- 扣减前按 `productId` 排序，保证所有订单以相同顺序加锁，降低死锁概率；
- 扣减成功写 `inventory_record` 流水（变动前、变动后、类型、订单号），可追溯。

**③ 支付幂等：三重保险**

1. 已 `SUCCESS` 直接返回；
2. `UPDATE ... WHERE status = 'PENDING'`，影响 0 行进入下一步；
3. 再查一次，若已是 `SUCCESS` 仍幂等返回，否则报"状态已变化"。

订单同样用 `WHERE status = 'PENDING_PAYMENT'` 条件更新为 `PAID`，避免重复支付把状态改乱。

**④ 回补：取消与售后**

- 用户取消（仅待支付）：库存 `+quantity`，写 `ORDER_CANCEL` 流水；
- 店员取消已支付订单：回补库存 + 退款 + 回减销量，一步不落；
- 售后同意：支付记录置 `REFUNDED`、库存回补、销量回减；
- 销量回减用 `CASE WHEN sales_count >= ? THEN sales_count - ? ELSE 0 END`，不会出现负数。

**⑤ 缓存一致性**

扣减/回补/加销量后，统一删除商品详情缓存和热销榜缓存（Cache Aside：写时删，而不是写时更新）。

### 3.3 追问速答

- **为什么不用 `synchronized` 或分布式锁？** 单库场景下一条条件 UPDATE 已经足够，锁会降低吞吐；只有分库分表后才需要分布式锁/库存分桶。
- **会不会死锁？** 多商品按商品 ID 排序扣减，统一加锁顺序，基本规避。
- **`version` 字段干什么？** 商品编辑用乐观锁，防止管理员并发修改互相覆盖；库存扣减靠 `stock >= ?` 已足够。

## 问题 4：难点三——前后端分离下，认证怎么可撤销、权限怎么防越权

**一句话答案：**
JWT 只证明"你是谁"，每次请求都回查数据库并用 Redis 白名单确认"你现在还能不能用"；URL 级按角色拦截，Service 再按数据归属拦截，前后端双层。

### 4.1 难在哪

1. 纯 JWT 无法主动失效：用户退出、账号被禁用，旧 token 仍在有效期内。
2. 角色写进 token 后，管理员改了角色，旧 token 还是旧权限。
3. 只做 URL 级鉴权防不住"customer A 看 customer B 的订单"。

### 4.2 怎么解决

**① 可撤销：jti + Redis 白名单**

- 签发时生成唯一 `jti`，Redis 存 `auth:session:{jti} = userId`，TTL 与 token 一致；
- 登出删除该 key；之后同一 token 请求，白名单查不到 → 当匿名 → 401；
- Redis 不可用时降级到进程内 Map，并节流打 WARN，保证可用性。

**② 角色/状态以数据库为准**

- 过滤器每次用 `sub` 回查用户，取最新 `role`、`status`；
- 账号被禁用 → `isEnabled()` false → 不建立认证 → 401；
- 角色被改 → 立即用新角色鉴权，不用等 token 过期。

**③ 双层授权**

| 层 | 做什么 | 例子 |
| --- | --- | --- |
| URL 级 | 按路径前缀限制角色 | `/api/admin/**` 仅 ADMIN；`/api/staff/**` 允许 STAFF/ADMIN |
| 数据级 | 校验资源是否属于当前用户 | 订单查询强制 `user_id = 当前用户` |

数据级越权返回 **404** 而不是 403，避免攻击者枚举"哪些订单 ID 真实存在"。

**④ 统一 401/403**

- 未登录/过期/被撤销/被禁用 → 401 `{"code":401,"message":"未登录或登录已过期"}`；
- 已登录但角色不够 → 403 `{"code":403,"message":"没有访问权限"}`；
- 前端对 401 统一清登录态并跳登录页（带 redirect），对 403 只提示无权限。

### 4.3 追问速答

- **Redis 挂了会不会全部登出？** 不会，降级到本机会话缓存；读 Redis 异常时放行（可用性优先），这是明确取舍。
- **Token 能提前失效吗？** 登出可以；改密目前不会自动撤销旧 token，是已知改进项。
- **前端隐藏按钮算权限吗？** 不算，只是体验；真正的边界在后端，下面第 6 问有 403 演示。

## 问题 5：挑一个功能，从前端到数据库讲一遍——「新增用户」

**一句话答案：**
管理员弹窗表单（Zod 校验）→ `POST /api/admin/users` → 后端角色拦截 + `@Valid` 校验 → Service 查重、BCrypt 加密、落库 → 返回 UserVO → 前端 Toast 并刷新列表。

### 5.1 一条主线（背这张表）

| 步骤 | 位置 | 做了什么 |
| --- | --- | --- |
| 1 | `admin-users-page.tsx` → `CreateUserDialog` | 打开"新建用户"弹窗，默认角色 CUSTOMER |
| 2 | React Hook Form + Zod | 提交前校验用户名、密码、昵称、手机号、邮箱、角色 |
| 3 | `adminService.createUser(body)` | 调用 `api.post("/admin/users", body)` |
| 4 | `api-client.ts` | 自动加 `Authorization: Bearer <token>`、JSON 头、15 秒超时 |
| 5 | `SecurityConfig` + `JwtAuthenticationFilter` | 验签、回查用户、校验 `ROLE_ADMIN` |
| 6 | `UserController.create(@Valid @RequestBody ...)` | 参数绑定 + Bean Validation；AOP 记录操作日志 |
| 7 | `UserService.create()` | 用户名查重 → BCrypt 加密 → 补默认值 → 设置角色/状态 |
| 8 | `UserMapper.insert()` | MyBatis-Plus 插入 `sys_user`，自增 ID 回填 |
| 9 | 返回 `ApiResponse<UserVO>` | 前端 `onSuccess` 弹 Toast、刷新用户列表、关闭弹窗 |

### 5.2 前端做了什么

**表单规则（Zod）**

| 字段 | 规则 |
| --- | --- |
| username | 3-30 位，只允许字母、数字、下划线 |
| password | 6-32 位 |
| nickname | 可选，≤ 30 字 |
| phone | 可选，`1[3-9]` 开头 11 位 |
| email | 可选，标准邮箱格式 |
| role | 枚举 `CUSTOMER / STAFF / ADMIN` |

细节：

- 角色用 `Controller` + `CustomSelect`（自定义组件不转发 ref，不能直接 `register`）；
- 错误通过 `errors.username?.message` 渲染在字段下方；
- 提交时 `trim()`，空字符串转 `undefined`，避免把 `""` 传给后端；
- 成功后 `invalidateQueries(["admin","users"])`，列表自动刷新。

**请求层**

- 有 token 就加 `Authorization`，没有就匿名；
- 后端返回 `code !== 200` 时抛 `ApiError`，页面 `onError` 统一 `toast.error("创建用户失败", 后端message)`。

### 5.3 接口契约

```http
POST /api/admin/users
Authorization: Bearer <admin-token>
Content-Type: application/json

{
  "username": "staff02",
  "password": "staff123",
  "nickname": "店员小周",
  "phone": "13800138000",
  "email": "staff02@example.com",
  "role": "STAFF"
}
```

成功：

```json
{
  "code": 200,
  "message": "success",
  "data": { "id": 21, "username": "staff02", "nickname": "店员小周", "role": "STAFF", "status": "ENABLED" },
  "timestamp": 1762300000000
}
```

失败（用户名重复，HTTP 409）：

```json
{ "code": 1001, "message": "用户名已存在", "timestamp": 1762300000000 }
```

### 5.4 后端做了什么

**Controller**

```java
@PostMapping
@OperationLogRecord(module = "用户管理", operation = "创建用户", saveParams = false)
public ApiResponse<UserVO> create(@Valid @RequestBody AdminUserCreateRequest request) {
    return ApiResponse.ok(userService.create(request));
}
```

- `@Valid` 触发 DTO 注解校验（用户名 3-30 + 正则、密码 6-32、角色枚举正则等）；
- `saveParams = false` 表示不记录请求参数，避免密码进日志；AOP 仍记录操作人、IP、耗时、成功/失败。

**Service（`@Transactional`）**

1. `selectCount(username = ?)` → 大于 0 抛 `1001 用户名已存在`；
2. `passwordEncoder.encode(password)`：BCrypt 加盐哈希；
3. 昵称为空则默认用用户名；手机号/邮箱空串转 `null`；
4. `role` 用 `UserRole.valueOf()` 转枚举，非法值在 DTO 正则阶段就被拦；
5. 状态固定 `ENABLED`（新建即可登录）；
6. `userMapper.insert(user)`；
7. 再 `selectById` 查回完整记录，转 `UserVO`（**不返回密码字段**）。

**数据库**

- `sys_user.username` 唯一键 `uk_user_username`，即使并发绕过 Service 查重，也会被数据库拦住；
- 唯一键冲突由全局异常处理转成 409 `"数据已存在，请勿重复提交"`；
- `created_at`、`deleted` 有默认值，插入无需手工赋值。

### 5.5 失败了前端怎么提示

| 失败场景 | 后端返回 | 前端表现 |
| --- | --- | --- |
| 用户名 2 位、密码 3 位 | 不发请求 | 输入框下方红字："用户名为 3-30 位…""密码至少 6 位" |
| 角色不是枚举值 | 400 `code=400` | Toast："创建用户失败" + 具体字段提示 |
| 用户名已存在 | 409 `code=1001` | Toast："创建用户失败 / 用户名已存在" |
| 非管理员调用 | 403 `code=403` | Toast："创建用户失败 / 没有访问权限" |
| token 过期 | 401 `code=401` | 全局拦截：提示"登录已过期"并跳登录页（带 redirect） |
| 后端没启动/超时 | 无响应 | Toast："无法连接服务器…"或"请求超时…" |
| 并发重名撞唯一键 | 409 `code=409` | Toast："数据已存在，请勿重复提交" |

### 5.6 追问速答

- **参数怎么校验的？** 前端 Zod（体验）→ 后端 `@Valid`（契约）→ Service 查重（业务）→ 数据库唯一键（兜底），四层。
- **密码安全吗？** BCrypt 加盐哈希，数据库不存明文；返回 VO 不含密码；日志不记参数。
- **为什么不用注册接口建店员？** 注册接口强制 `CUSTOMER`，防止用户自己提权；管理员建号是独立接口，受 `ROLE_ADMIN` 保护。
- **事务有必要吗？** 单条 insert 本身原子，但"查重 + 插入"放在同一事务里语义更清晰；真正的并发兜底是唯一键。
- **为什么返回 UserVO 而不是实体？** 实体含密码字段，直接返回会泄露；VO 只暴露前端需要的字段。

## 问题 6：登录 / 权限是怎么做的

**一句话答案：**
BCrypt 校验密码 → 签发带 `jti` 的 JWT 并写入 Redis 白名单 → 每次请求过滤器验签、回查用户、查白名单 → URL 级角色拦截 + Service 数据归属校验。前端只做"不打扰用户"的隐藏。

### 6.1 登录 8 步

1. `POST /api/auth/login`，`@Valid` 校验非空；
2. `AuthenticationManager` 认证 → `UserDetailsServiceImpl` 按用户名查库；
3. BCrypt 比对密码；账号 `DISABLED` 抛 `DisabledException`；
4. 生成 JWT：`jti`、`sub=userId`、`username`、`role`、`iss`、`iat`、`exp`；
5. `TokenStore.store(jti, userId, ttl)` 写 Redis；
6. 返回 `{token, tokenType:"Bearer", expiresIn, user}`；
7. 前端存 localStorage，Zustand 置已登录，清空旧查询缓存；
8. 后续请求自动带 `Authorization: Bearer <token>`。

失败：`1003 用户名或密码错误`（401）、`1004 账号已被禁用`（403）。不区分"用户不存在"和"密码错"，防账号枚举。

### 6.2 权限三层

| 层 | 实现 | 失败表现 |
| --- | --- | --- |
| 前端路由 | `RequireAuth` / `RequireRole` | 跳登录 / 403 页面 |
| 前端动作 | `can()`、导航按角色过滤 | 按钮、菜单不渲染 |
| 后端 URL | `SecurityConfig` 按前缀 `hasRole` | 401 / 403 JSON |
| 后端数据 | Service 校验 `user_id` 等归属 | 404 / 403 业务码 |

后端规则（顺序敏感）：

```java
.requestMatchers("/api/auth/login", "/api/auth/register").permitAll()
.requestMatchers(HttpMethod.GET, "/api/products/**", "/api/recommendations/**",
        "/api/reviews/products/**", "/api/dict/**", "/api/appearance/**").permitAll()
.requestMatchers("/api/admin/**").hasRole("ADMIN")
.requestMatchers("/api/staff/**").hasAnyRole("STAFF", "ADMIN")
.anyRequest().authenticated()
```

### 6.3 现场演示：普通账号调管理接口返回 403

```powershell
# 1. customer 登录
$c = Invoke-RestMethod -Method Post -Uri "http://localhost:8080/api/auth/login" `
     -ContentType "application/json" -Body '{"username":"customer","password":"customer123"}'

# 2. 用它调管理员接口
curl.exe -i "http://localhost:8080/api/admin/users" -H "Authorization: Bearer $($c.data.token)"
# 期望：HTTP/1.1 403 + {"code":403,"message":"没有访问权限"}

# 3. 不带 token 调订单接口
curl.exe -i "http://localhost:8080/api/orders"
# 期望：HTTP/1.1 401 + {"code":401,"message":"未登录或登录已过期"}
```

再补一句：**前端把按钮删了也没用**，接口是公开地址，curl 照样能打，所以安全边界必须在后端。

### 6.4 Token 过期会怎样

- 默认有效期 **86400 秒（24 小时）**，可用 `JWT_EXPIRATION` 调整；
- 过期后 `JwtService.parse()` 直接抛异常 → 过滤器清空上下文 → 匿名 → **401**；
- 前端有三重处理：
  1. 任意请求 401 → 清登录态 + Toast + 跳登录（带 redirect 回原页）；
  2. 到期前 **60 秒**定时器主动提示"登录状态即将过期"；
  3. 刷新页面用 `/api/auth/me` 恢复登录态，失败即视为未登录。

### 6.5 有没有刷新机制（要如实说）

**现状：没有 refresh token。** 单令牌 24 小时，过期后重新登录。这是取舍：项目核心是推荐与业务闭环，认证优先"简单 + 可撤销"。

**如果要做无感刷新，我会这样加：**

- access 短（15-30 分钟）+ refresh 长（7-30 天）；
- `POST /api/auth/refresh` 做**轮换**：每次刷新作废旧 refresh，发新的；
- 旧 refresh 被再次使用 → 判定泄露，撤销整个令牌族，强制重新登录；
- refresh 只存哈希（SHA-256），并放 HttpOnly Cookie；
- 前端并发 401 时只允许一个请求去刷新，其余排队等新 token。

这样回答既承认现状，又给出完整方案。

## 问题 7：核心表有哪些，表之间怎么关联

**一句话答案：**
14 张表，按 6 个域组织：用户、商品与库存、交易、评价、推荐、运维。三个中心是 `sys_user`、`product`、`shop_order`，共 16 条外键。

### 7.1 表清单

| 域 | 表 | 作用 |
| --- | --- | --- |
| 用户 | `sys_user` | 账号、BCrypt 密码、角色、状态、头像 |
| 商品 | `product` | 商品主数据：价格、库存、销量、评分、标签、季节 |
| 商品 | `inventory_record` | 库存变动流水（入库/下单扣/取消回补/人工调整/售后退回） |
| 交易 | `cart_item` | 购物车（用户 × 商品唯一） |
| 交易 | `user_favorite` | 收藏（用户 × 商品唯一） |
| 交易 | `shop_order` | 订单主表：金额、状态、收货信息、售后原因 |
| 交易 | `order_item` | 订单明细，保存下单时的商品快照 |
| 交易 | `payment_record` | 支付单（模拟支付、幂等回调） |
| 交易 | `fulfillment_record` | 履约节点流水（接单/备货/配送/签收） |
| 评价 | `review` | 评分、内容、管理员回复、可见性 |
| 推荐 | `recommendation_weight` | 四维权重配置（单行） |
| 推荐 | `recommendation_log` | 推荐上下文、权重快照、结果明细 |
| 运维 | `operation_log` | AOP 操作日志（人、接口、参数、耗时、成败） |
| 运维 | `appearance_setting` | 登录/注册页背景外观（单行） |

### 7.2 关联关系

```
sys_user ──< cart_item >── product
sys_user ──< user_favorite >── product
sys_user ──< shop_order ──< order_item >── product
                  │              └──< review（一条明细最多一条评价）
                  ├──< payment_record
                  ├──< fulfillment_record
                  └──< review

product ──< inventory_record
sys_user ──< recommendation_log
```

16 条外键：

| 子表 | 外键 | 父表 |
| --- | --- | --- |
| inventory_record | product_id | product |
| cart_item | user_id / product_id | sys_user / product |
| user_favorite | user_id / product_id | sys_user / product |
| shop_order | user_id | sys_user |
| order_item | order_id / product_id | shop_order / product |
| payment_record | order_id / user_id | shop_order / sys_user |
| fulfillment_record | order_id | shop_order |
| review | order_id / order_item_id / user_id / product_id | shop_order / order_item / sys_user / product |
| recommendation_log | user_id | sys_user |

`recommendation_weight`、`operation_log`、`appearance_setting` 不建外键（配置/审计表，要求独立留存）。

### 7.3 三条主线（老师最爱顺着问）

**下单线：**
`sys_user` → `shop_order` → `order_item` → `product`，同时 `payment_record`、`fulfillment_record` 挂订单，`inventory_record` 挂商品。

**评价线：**
`order_item` 1:0..1 `review`，`review` 同时关联 `shop_order`、`sys_user`、`product`；唯一键 `uk_review_order_item` 防重复评价。

**推荐线：**
`sys_user` 的购买（`order_item`）、收藏（`user_favorite`）、评价（`review`）构成画像输入，结果写 `recommendation_log`，权重来自 `recommendation_weight`。

### 7.4 设计要点（追问用）

- **订单明细为什么冗余商品名/单价？** 订单是历史凭证，商品改价改名不能影响已成交订单。
- **为什么不加 `ON DELETE CASCADE`？** 系统用逻辑删除，物理删除极少；不级联可以防止"删用户带走一批订单"。
- **重复加购/重复收藏怎么防？** 联合唯一键：`uk_cart_user_product`、`uk_favorite_user_product`。
- **订单号、支付单号唯一吗？** `uk_order_no`、`uk_payment_no` 唯一，天然防重复。
- **为什么日志表不建外键？** 审计要长期保留，不能被业务数据删除牵连。
- **库存为什么单独一张流水表？** 任何一次库存变化都能回答"谁、何时、因为什么、从多少变到多少"。
