# 一个功能走完全链路：加入购物车

> 答辩口径：前端控件限制 → `POST /api/cart/items` → Controller 校验 → Service 业务判断 → Mapper 写 `cart_item` → 返回 VO → 前端 Toast 并刷新角标。
> 本文所有路径均对应当前仓库源码。

---

## 一、30 秒版本（先背这张表）

| 步骤 | 位置 | 做什么 |
| --- | --- | --- |
| 1 | `frontend/src/pages/product-detail-page.tsx` | 选择数量，上限 `min(99, 库存)` |
| 2 | 同上 `handleAdd` | `requireLogin()` 拦住未登录用户 |
| 3 | `frontend/src/lib/services.ts` | `cartService.add()` → `POST /cart/items` |
| 4 | `frontend/src/lib/api-client.ts` | 自动加 `Authorization: Bearer`、JSON 头、15 秒超时 |
| 5 | `CartController.add()` | `@Valid @RequestBody CartAddRequest` |
| 6 | `CartService.add()` | 查商品、校验在售、查库存、已有行则累加 |
| 7 | `CartItemMapper` | `insert` 或 `updateById`，写 `cart_item` |
| 8 | 返回 `CartItemVO` | 前端 Toast「已加入购物车」+ 刷新购物车角标 |

真实接口是 **`POST /api/cart/items`**（不是 `/api/cart`）。

## 二、前端做了什么

### 1. 数量控件：从源头限制范围

`frontend/src/pages/product-detail-page.tsx:186-190`

```tsx
const soldOut = data.stock <= 0;
const maxQuantity = Math.min(99, data.stock);
```

`product-detail-page.tsx:267-291`

```tsx
<Button disabled={quantity <= 1 || soldOut}
        onClick={() => setQuantity((v) => Math.max(1, v - 1))}>-</Button>

<Button disabled={quantity >= maxQuantity || soldOut}
        onClick={() => setQuantity((v) => Math.min(maxQuantity, v + 1))}>+</Button>
```

要点：

- 数量最小 1，最大 `min(99, 当前库存)`；
- 售罄时加减和加购按钮都禁用；
- 加购按钮 `disabled={soldOut || addMutation.isPending}`，防止连点重复提交。

## 三、接口契约

```http
POST /api/cart/items
Authorization: Bearer <token>
Content-Type: application/json

{ "productId": 1, "quantity": 2 }
```

成功：

```json
{
  "code": 200,
  "message": "success",
  "data": {
    "id": 12,
    "productId": 1,
    "productName": "经典红玫瑰礼盒·11朵",
    "price": 199.00,
    "quantity": 2,
    "subtotal": 398.00,
    "stock": 120,
    "status": "ON_SALE",
    "available": true
  },
  "timestamp": 1762300000000
}
```

`CartItemVO` 里有两个字段值得讲：

- `subtotal = price × quantity`；
- `available = 在售 && stock >= quantity`，购物车页用它判断能否结算。

常用错误：

| 场景 | HTTP | code | message |
| --- | --- | --- | --- |
| 未登录 / token 过期 | 401 | 401 | 未登录或登录已过期 |
| 商品不存在 | 404 | 2001 | 商品不存在 |
| 商品已下架 | 409 | 2002 | 商品已下架 |
| 库存不足 | 409 | 2003 | 商品「xx」库存不足，当前库存 N |
| 数量不在 1~99 | 400 | 3003 | 单件商品购买数量需在 1-99 之间 |
| 并发插重复行 | 409 | 409 | 数据已存在，请勿重复提交 |

## 四、后端逐层

### 1. Controller：只做收参与转发

`backend/src/main/java/com/flower/mall/module/cart/controller/CartController.java:37-41`

```java
@PostMapping("/items")
public ApiResponse<CartItemVO> add(@Valid @RequestBody CartAddRequest request) {
    return ApiResponse.ok(cartService.add(request));
}
```

类上 `@RequestMapping("/api/cart")`，所以完整路径是 `/api/cart/items`。

### 2. DTO：Bean Validation 校验形状

`backend/src/main/java/com/flower/mall/module/cart/dto/CartAddRequest.java`

```java
@NotNull(message = "商品ID不能为空")
private Long productId;

@NotNull(message = "数量不能为空")
@Min(value = 1, message = "数量必须大于0")
@Max(value = 99, message = "单次最多购买99件")
private Integer quantity;
```

`@Valid` 失败 → `MethodArgumentNotValidException` → 全局异常处理 → HTTP 400，`message` 直接是注解里的中文。

### 3. Service：真正的业务判断

`backend/src/main/java/com/flower/mall/module/cart/service/CartService.java:42-64`

```java
@Transactional
public CartItemVO add(CartAddRequest request) {
    Long userId = SecurityUtils.currentUserId();
    Product product = productMapper.selectById(request.getProductId());
    validateProduct(product, request.getQuantity());

    CartItem existing = cartItemMapper.selectOne(... userId + productId ...);
    if (existing != null) {
        int targetQuantity = existing.getQuantity() + request.getQuantity();
        validateStock(product, targetQuantity);
        existing.setQuantity(targetQuantity);
        cartItemMapper.updateById(existing);
        return CartItemVO.from(existing, product);
    }

    CartItem item = new CartItem();
    item.setUserId(userId);
    item.setProductId(request.getProductId());
    item.setQuantity(request.getQuantity());
    cartItemMapper.insert(item);
    return CartItemVO.from(item, product);
}
```

`CartService.java:132-151` 的校验顺序：

1. 商品是否存在 → `2001`；
2. 是否 `ON_SALE` → `2002`；
3. 数量是否在 1~99 → `3003`；
4. 数量是否超过库存 → `2003`。

**重复加购不是插新行**，而是把数量累加后再校验一次库存和 99 上限。

### 4. Mapper / Entity / 表

`CartItemMapper` 直接继承 `BaseMapper<CartItem>`，没有手写 SQL：

```java
@Mapper
public interface CartItemMapper extends BaseMapper<CartItem> {}
```

`CartItem` 用 `@TableName("cart_item")` 映射表，`@TableId(type = IdType.AUTO)` 自增主键。

`backend/db/schema.sql`：

```sql
CREATE TABLE cart_item (
    id BIGINT NOT NULL AUTO_INCREMENT,
    user_id BIGINT NOT NULL,
    product_id BIGINT NOT NULL,
    quantity INT NOT NULL,
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    PRIMARY KEY (id),
    UNIQUE KEY uk_cart_user_product (user_id, product_id),
    CONSTRAINT fk_cart_user FOREIGN KEY (user_id) REFERENCES sys_user (id),
    CONSTRAINT fk_cart_product FOREIGN KEY (product_id) REFERENCES product (id)
);
```

唯一键 `uk_cart_user_product` 保证“一个人一个商品只有一行”，是重复加购的最后一道防线。

## 五、参数怎么校验（四层）

| 层 | 位置 | 校验内容 | 失败表现 |
| --- | --- | --- | --- |
| 前端控件 | `product-detail-page.tsx` | 数量 1~`min(99,库存)`；售罄禁用；按钮 pending 防连点 | 点不动，不发请求 |
| Bean Validation | `CartAddRequest` + `@Valid` | `productId` 非空；`quantity` 1~99 | 400，字段提示 |
| Service 业务 | `CartService.add` | 商品存在、在售、库存足够、累加后仍不超限 | 2001/2002/2003/3003 |
| 数据库 | `cart_item` 唯一键 | 同一用户同一商品只有一行 | 409「数据已存在」 |

> 注意：这个功能没有表单，也没有 Zod；前端靠“加减按钮 + 禁用状态”限制，真正的边界在 `@Valid` + Service。老师若追问“为什么不用 Zod”，就答“加购不是表单输入，数量由受控按钮产生，用控件约束更自然；后端仍然会重新校验”。

## 六、失败了前端怎么提示

| 场景 | 后端返回 | 前端表现 |
| --- | --- | --- |
| 数量为 0 或超过 99 | 400 / 3003 | Toast「加入购物车失败 / 单件商品购买数量需在 1-99 之间」 |
| 未登录 | 前端直接拦截；直接调接口则 401 | Toast「请先登录」并跳登录页，带 redirect |
| 商品不存在 | 404 / 2001 | Toast 后端原文「商品不存在」 |
| 商品已下架 | 409 / 2002 | Toast「商品已下架」 |
| 库存不足 | 409 / 2003 | Toast「商品「xx」库存不足，当前库存 N」 |
| 并发重复插入 | 409 / 409 | Toast「数据已存在，请勿重复提交」 |
| 后端未启动 / 超时 | 无响应 | Toast「无法连接服务器…」或「请求超时…」 |
| token 过期 | 401 | 全局清登录态，跳登录页并回跳 |

前端统一入口：`toast.error("加入购物车失败", getErrorMessage(error))`，优先展示后端 `message`，没有才用兜底文案。

## 七、高频追问

**Q1：加购会扣库存吗？**
不会。只校验库存，不扣减。真正扣库存发生在“创建订单”，用 `UPDATE ... WHERE stock >= ?` 条件更新，避免购物车长期占库存。

**Q2：重复加购会怎样？**
查 `user_id + product_id`，已有行就 `existing.quantity + 本次数量`，然后重新校验 99 上限和库存，`updateById` 更新，不插新行。

**Q3：并发加购会不会出现两行？**
数据库有 `uk_cart_user_product`，第二个插入会触发 `DuplicateKeyException`，全局异常转 409；正常路径下先查后插，冲突概率很低。

**Q4：为什么上限是 99？**
业务约定，`CartAddRequest @Max(99)` 和 `CartService.MAX_QUANTITY_PER_PRODUCT = 99` 双重限制，避免恶意大数量。

**Q5：库存不足为什么不在前端拦住？**
前端只拿得到页面加载时的库存，库存可能已经被别人买走；以后端校验为准，前端提示只是体验。

**Q6：`@Transactional` 有必要吗？**
加购是单表单条写，事务不是必须，但保留可以保证“累加 + 更新”作为一个整体；真正需要事务的是下单扣多件库存。

**Q7：为什么返回 `CartItemVO` 而不是实体？**
实体只有 `userId/productId/quantity`，前端还需要商品名、价格、小计、库存、是否可结算；VO 把商品信息拼好，避免前端再查一次。

**Q8：这个功能能串到推荐吗？**
能。加购是比浏览更强的行为信号，可扩展进用户画像；当前推荐主要用购买、收藏、评价，加购可作为后续增强。

## 八、30 秒口述模板

> “用户在商品详情页选数量，前端把上限卡在 `min(99, 库存)`，售罄直接禁用。点加购先判断登录，然后 `POST /api/cart/items`，body 是 `productId + quantity`。后端 `@Valid` 校验数量和商品 ID，Service 查商品是否存在、是否在售、库存够不够；如果购物车已有这行，就把数量累加后再校验一次。最后 Mapper 执行 insert 或 updateById，返回 `CartItemVO`，前端 Toast 并刷新购物车角标。加购只校验不扣库存，下单时才真正扣减。”
